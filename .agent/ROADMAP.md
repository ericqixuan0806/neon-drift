# Neon Drift 全面优化路线图

范围：继续维护唯一游戏源码 [`../neon-drift.html`](../neon-drift.html)，保持无需构建即可运行的单文件 Canvas 架构。修改仅限本项目目录。UI 依据 [`../design/Neon Drift Visual Style Guide.docx`](../design/Neon%20Drift%20Visual%20Style%20Guide.docx)。本轮按用户既有要求不使用 Astra；计划来自源码检查、当前项目记录和下列一手资料。

## 现状与研究结论

- 已有功能包括普通/每日挑战、六个主题、Boss、升级/技能、任务/成就、统计、八款飞船外观、设置、版本化存档和无障碍 DOM 控件。现有 15 项自动检查全部通过；已有自动检查覆盖了存档核心、状态切换、失焦清理、可访问控件和配色切换。
- 代码级缺口：`localStorage` 方法内部有异常处理，但访问浏览器全局 `localStorage` 属性本身未受保护；若浏览器/隐私策略让属性读取抛错，初始化仍会提前终止。系统减少动态效果只关闭了震屏，菜单滑动、拾取脉动、关卡闪光等非必要动效仍在运行。
- 交互风险：Canvas 显式移除了 outline，聚焦 Canvas 时没有明显焦点指示；现有 DOM 操作区可键盘访问，但未对这一入口做回归覆盖。画布交互依靠 Pointer Events，已有 pointercancel 和失焦清理，补足取消/resize/偏好设置回归检查。
- 视觉边界：深色太空底、青色安全/正向、粉色危险、金色奖励、Orbitron 与 Chakra Petch、彩色匹配辉光、画布逻辑缩放和安全区均为现有设计契约。优化不改变危险/奖励颜色语义，不凭静态审阅改变价格、难度或奖励节奏。
- 相似游戏参考：官方《Super Hexagon》页面将其描述为极简动作游戏；这支持保持“目标清楚、启动快、重开短”的街机主循环作为参考方向，但不构成它与 Neon Drift 的玩法/平衡相同的证据，也不据此抄用难度或内容。[Steam 官方页面](https://store.steampowered.com/app/221640/Super_Hexagon/)；[开发者官网](https://superhexagon.com/)
- 输入与适配：W3C WCAG 2.2 SC 2.5.8 将指针目标最小尺寸设为 24×24 CSS px，或满足规定间距例外；Microsoft Xbox Accessibility Guidelines 建议菜单和游戏输入可由单次数字输入操作，并提供合适的替代输入；MDN 说明 Pointer Events 统一鼠标、触屏和触控笔，`pointercancel` 也必须按中断处理。[W3C 目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)；[Xbox 输入指南](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/107)；[MDN Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events)
- 生命周期：MDN 文档说明隐藏页通常暂停 `requestAnimationFrame()`；现有代码已在 `visibilitychange` 时暂停并释放输入，本轮将守住这个行为并验证窗口变化/取消事件路径。[MDN Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)；[MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)
- 减少动态效果：样式规范明确要求系统请求减少动态效果时不震屏；本轮将把系统偏好扩展至非必要 UI 动效，并保留躲避游戏本身必要的物体运动。[W3C 动画交互理解](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)

## 分阶段工作、验收和执行记录

### 阶段 0：建立可复现基线

- 确认项目唯一入口、源码、设计约束、自动检查和 GitHub Pages 仓库文件。
- 验收：现有 `node --test tests/save-state.test.cjs` 通过；GitHub `main` 的源码与本地基线一致后才更新文件。

### 阶段 1：存档与浏览器能力容错

- 将 `localStorage` 全局获取集中成受保护的能力探测；属性不可访问时提供抛出型内存回退，使游戏可进入菜单/开局且不覆盖任何存档。
- 统一普通最佳分、每日最佳分、外观和正式存档写入所用的安全存储对象。
- 新增测试，覆盖 `localStorage` getter 抛错、读取/写入方法抛错、在内存回退下开始游戏，以及原有损坏数据不覆盖行为。
- 验收：脚本语法通过，针对场景全绿，现有存档恢复策略不回归。
- 结果：通过。16/16 自动检查通过；getter 抛错时进入只读模式，仍可开始游戏和切换本地内存外观，不写入存档。

### 阶段 2：减少动态效果和键盘焦点

- 系统 `prefers-reduced-motion` 开启时，关闭屏幕震动、装饰性拾取脉动、菜单滑入、关卡白闪和非必要慢动作；危险/奖励提示仍用既有形状、颜色与文本区分，躲避游戏必需运动照常。
- 为键盘聚焦的 Canvas 加上符合霓虹规范的可见焦点轮廓；保留隐藏 DOM 操作区聚焦后展开、金色键盘焦点。
- 新增 `prefers-reduced-motion` 真/假两种偏好测试及 Canvas 焦点样式存在性检查。
- 验收：测试确认系统偏好确实影响相应效果状态，普通偏好不改变既有画面状态机；视觉令牌不漂移。
- 结果：通过。19/19 自动检查通过；系统偏好生效于动态动画/装饰、震屏、关卡闪白、死亡慢放；设置改变时会即时应用，减少动态效果下死亡直接进入结束画面。普通偏好保留原效果。

### 阶段 3：输入与页面生命周期回归

- 将指针中断、键盘失焦和页面隐藏统一到输入释放流程；Canvas resize 时保持逻辑缩放、玩家位置范围和画布 DPR 限制。
- 对 pointerup/cancel、键盘按住后隐藏、resize、普通和减少动态效果配置分别进行确定性模拟测试。
- 维持非游戏状态不接受游戏操作，维持 Tab 可到达操作区；不要用自动模拟代替真实触屏验收。
- 验收：相应回归检查全绿，页面隐藏时游戏暂停且方向键/拖动状态清空，resize 后几何值有限且玩家仍在可玩区域。
- 结果：通过。21/21 自动检查通过；pointercancel 清除拖动，失焦/隐藏清理方向键并暂停，resize 后 Canvas DPR 不超过 2 且几何/飞船位置有效。

### 回归修复：首帧游戏画面中断（2026-10-09）

- 复现：脚本编译和初始化均通过，但执行首个 `requestAnimationFrame` 时在 `draw()` 抛出 `ReferenceError: n is not defined`；背景板已绘制，随后游戏主菜单/前景停止渲染。
- 根因：减少动态效果改动把背景动画时间变量定义在 `bgd()` 的局部作用域，`draw()` 的星点和速度条也使用 `n`，因此首帧进入前景绘制就中止。
- 修复：在 `draw()` 建立自身的动效时间值，并继续经 `motion()` 遵循减少动态效果偏好。
- 回归检查：模拟完整执行首帧，并绘制主菜单、升级、关卡、任务、统计、设置、游玩、暂停、结束和重试状态；`node --test tests/save-state.test.cjs` 23/23 通过。
- 发布状态：已同步到 GitHub `main` 并回读匹配。修复源码提交 `e66b43398c7841b05d4d4b3f85e830ebe4199864`，绘制回归测试提交 `ec90c61052c4281f3a97744aa1a397becf897a6b`。

## 长期开发周期：Playable Release Quality（2026-10-09）

### 高标准目标

在保留现有近黑底、青色反馈、粉色危险、金色奖励、霓虹发光、字体、游戏规则、单文件入口和存档格式的前提下，让完整玩家旅程没有输入或导航死路：从主菜单进入商店与关卡、购买升级/技能、开始并操控一局、暂停/继续、应对首领、结束/重试、刷新恢复进度。Canvas 鼠标/触控、键盘与辅助 DOM 控件调用同一组有状态保护的动作。验收标准是约定的核心动作矩阵 100% 有可达路径且有确定性回归检查，并且没有已知首帧异常、存档丢失或导航死路。

### 研究和设计边界

- 研究样例用于检查街机游戏的聚焦体验和操作预期，不据此照搬风格、难度或经济系统。已存在的 Super Hexagon 参考只支持保持简洁的街机定位，不支持改变本游戏平衡。
- W3C Button Pattern 规定焦点按钮可由 Enter/Space 激活；游戏级快捷键不得截走这些原生操作。[W3C Button Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/)
- W3C WCAG 2.2 SC 2.5.8 的最小指针目标为 24×24 CSS px 或满足其间距例外；新增焦点操作继续复用现有暗底、青框和金色焦点，不遮挡主游戏。[W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)
- MDN Pointer Events 说明 pointer id 用来区分不同输入点，捕获会在 pointerup/pointercancel 时释放；每根手指的结束/取消只清理自己的拖动状态。[MDN Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events)；[setPointerCapture](https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture)
- 不更改 `{version:1,data:...}`、`neon-drift-meta`、普通/每日日期语义、价格奖励、难度、碰撞尺寸或解锁条件；除非测试暴露确凿回归，不做游戏平衡猜测。
- 本轮仅改 Neon Drift 项目内源码、测试、说明与计划。继续保留不依赖构建工具的独立 HTML。

### 阶段顺序

详细交付、依赖、输入矩阵和通过标准见 [MILESTONES.md](./MILESTONES.md)。顺序为：M0 锁定动作/状态验收矩阵；M1 共享动作和指针/键盘归属；M2 补齐辅助 DOM 的购买、分页、首领继续和技能操作；M3 补齐短而准确的帮助与结算反馈；M4 跑完整回归、文档核验并发布。

## 12 世界分段 Boss 战役（规划 v1.1 · 2026-10-10）

### 高标准目标

把现在的 12 个主题 Level 改造成可分次游玩、能保存进度的完整战役：每个主题世界包含 5 个小关卡，随后进入单独的大 Boss 关；击败 Boss 后出现世界胜利结算，玩家确认后进入下一个主题。推荐解释为 **12 世界 × (5 小关 + 1 Boss) = 60 小关 + 12 个 Boss，共 72 个可达节点**。前 11 个世界的 Boss 结算通向下一世界；第 12 个 Boss 显示明确的战役最终结局，并由玩家选择返回菜单或另行进入无尽模式。

目标验收是整个战役可从任一已保存节点恢复、可击败全部 12 个主题 Boss、各状态转换/奖励只提交一次、旧进度不丢失、难度不因总时长提早饱和，且 UI 继续符合既有霓虹视觉规范。Browser/device 与实际游玩平衡需分别实测，不能由 Canvas VM 测试替代。

### 已确认事实、假设和开放决定

- **已确认：**唯一运行入口是单文件 `neon-drift.html`。12 个 `TH` 主题当前各映射一段 25 秒 Level，12 段共 300 秒。每主题已有两个 Boss 名称 `BN`，Boss 画面沿用当前几何/发光风格。
- **已确认：**Normal 的 Boss 现在由全局计时触发（首次约 88 秒，此后约 80 秒）；Wave 每约 28 秒触发。两者都与当前 25 秒主题边界无关。Boss 击败现即时发奖励并进入 `win`，Continue 会恢复同一局。
- **已确认：**总时间 `t` 还影响移动速度、刷怪间隔、墙缝宽度和追踪障碍启用；`bc` 影响 Boss 生命和弹幕。仅替换关卡索引不足以支持 72 节点。
- **已确认：**版本1 `M.lv` 最多 12 项，每项为旧主题成绩字段；校验只保留已知字段；`.cl` 代表旧版 25 秒生存段完成，不能直接当作新世界的大 Boss 已击败。
- **已确认：**永久状态会从多个路径变化：拾取、Boss、Wave、任务、成就、Run 结束和个人最佳分。`mode`（Daily）和 `gm`（Normal/Hardcore/Zen）目前分开。
- **推荐假设：**每个现有主题即一个世界；“每五个小关卡结束后会有一个关卡有大 Boss”解释为五个小关之后另有第六个 Boss 节点。若用户原意是五个节点内含 Boss，需在 M0 改为 4 小关 + Boss（60 节点），不可默默混用。
- **时长实验值：**以 20 秒作为 M2 竖切的默认参数；同时试玩 15/20/25 秒三个时长。60 个小关的纯生存时长分别为 15/20/25 分钟，另加 12 场 Boss 与转场。5 秒虽然能把现有 25 秒分成五段，但每段转换过密，建议不作为初版；这些是产品假设，不是研究证明的最佳时长。M0 记录推荐值和条件；M2 后根据实玩决定正式数值。M0 同时锁定复玩是否可领取普通金币（推荐首次收益每存档仅一次、复玩只刷成绩）及独立统计字段定义。

### 调研结论与设计依据

- Game Developer 的 Boss 战设计文章把 Boss 描述为检验已学技能的里程碑，并建议在战前逐渐建立张力、战后释放张力。**据此推导**五小关需要形成“认识/练习/变化/组合/预告”的节奏，Boss 胜利后给明确喘息与结算；资料没有规定本游戏应采用几秒一关。[Boss Battle Design and Structure](https://www.gamedeveloper.com/design/boss-battle-design-and-structure)
- Unity 对 *Evil Wizard* Boss 制作的开发复盘记录了先写行为与阶段、原型测试、调数值和完成后再集成的过程。**据此推导**本项目应先做一个完整世界竖切，再铺剩余主题；不应一开始批量造 12 套未经试玩的 Boss 机制。[How Rubber Duck Games developed a boss fight](https://unity.com/blog/games/how-rubber-duck-games-developed-a-boss-fight)
- Microsoft XAG 108 指出难度是玩家能力与障碍的交互，过高门槛会阻断后续内容。**据此推导**Normal 应有节点 checkpoint、Zen 应能完成可练习的 Boss 流程，并在 M2/M6 收集真实玩家表现；Node 自动覆盖不能定出理想难度。[XAG 108: Game difficulty options](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/108)
- Microsoft XAG 103 建议玩法关键讯息不要只靠颜色，要有形状/文字/音讯或播报等额外提示。**据此推导**Boss 预警和危险攻击应结合几何/位置、短文字和现有音频/无障碍播报；粉色可以继续表达 Boss/危险语义但不能成为唯一信号。[XAG 103: Game cues and color](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103)
- Super Hexagon 官方页将产品定位为极简动作游戏，强调速度与节奏。它适合用作“保留专注街机体验”的风格参照，**不提供 20 秒小关或 72 节点长度的依据**。[Super Hexagon](https://superhexagon.com/)

### 状态模型和保存方向

建议有明确的一套状态机，避免 `t`、`st`、旧 `bc` 和页面按钮各自猜测流程：

`world-entry → mini-node-entry → playing → node-clear → (Normal node-commit | Hardcore attempt-only) → next-mini-node`

第五小关之后为：

`boss-warning → boss-playing → world-clear → atomic-commit(rewards + next checkpoint + pendingSettlement) → victory-settlement → acknowledge/save → next-world-entry`

第 12 世界的 `world-clear` 进入 `campaign-final-settlement`。另有 `paused`、`node-failed`、`retry`、`save-error` 和从最终画面选择 `endless`。结算是已提交世界的只读回放；Continue 仅清除待展示结算，清除存档失败时继续停留，不重复发奖或开始模拟。节点切换/结束立即停止旧节点物理模拟。推荐同帧致死优先于 Boss kill/节点 clear；将这一帧事件归并后只作一个终态判决，避免迭代顺序同时发奖又 Game Over。

Campaign 难度按 `worldIndex + nodeIndex + nodeElapsed` 配置。Campaign 小关使用重置的节点内 `t` 推进速度/清关，独立配置事件比例、spawn cadence、安全墙隙及世界速度增量；Boss 使用独立数据配置移动、首击预警、射击间隔、攻击家族和伤害。Legacy/Daily/Endless 仍走旧调度。时间与数值暂为原型，最终由 M6 玩家对照决定。旧模式可以继续使用旧调度，必须由显式 `runKind=campaign|daily|endless|practice` 与 `difficulty=normal|hardcore|zen` 路由，不能依赖隐式的 `mode/gm` 组合。

存档采用 **schema v2**，仍用 `neon-drift-meta` 单主存档键并保留 v1 迁移：保留旧 `M.lv[0..11]` 原数据/索引/意义；独立 `campaign` 对象已实现唯一 checkpoint、12 世界记录、稳定首通 claim、运行次数和待展示结算字段。Campaign 状态转换现已接入实际节点循环；Normal 节点/Boss 提交、Hardcore 世界 attempt、Zen Assisted 清关与结算确认均有自动回归覆盖。旧 `.cl` 仅作为旧版成绩，不伪造 Boss 通关；新战役默认从 World 1 开始。迁移先备份原始 v1；备份失败不覆盖主档，进入只读/内存继续并允许导出；损坏/未来 schema 仍原文保留。所有 Campaign 持久奖励必须在一个经过校验的 v2 快照中更新；Normal 节点 clear 视奖励及入口为一个事务，Hardcore 保留唯一世界入口直至该世界 Boss clear。结算内容是已提交收益的展示凭证，不是待二次发放的账单；Continue 绝不发奖励，只在清除 `pendingSettlement` 成功落盘后开始下个节点。若 Boss 首次清关事务写失败，则不显示已保存胜利、刷新回最后 checkpoint 且没有收益；若事务成功但结算 ack 写失败，则留在结算页，刷新仍显示同一已提交结果。Normal 节点 clear 提交失败时冻结 attempt，不启动下一节点；刷新回到上一个 checkpoint。localStorage 没有跨标签页事务承诺，首版记录为单活跃战役约束，测试和 UI 不宣称多标签无冲突。

#### 跨任务的内容与审美验收

- 每个世界沿用当前主题色、背景剪影、危险/Boss 几何和奖励语义；只能用轻量参数差异、既有攻击家族及低成本 Canvas 图形丰富节奏，不引入写实/卡通新素材或另一套 UI。
- 五小关的任务弧固定为“认识该主题危险 → 重复练习 → 单一变化 → 两种已学机制组合 → Boss 预告”；Boss 的主要招式应能在前五关辨认出前置线索，不能只靠数值堆高。
- Boss 胜利态必须冻结战斗；结算展示世界、Boss、获得/保存结果和下一步。下一世界仅由确认动作开启，最终 Boss 提供战役完成结算。结算与读屏播报不重复发奖。
- 一次任务结束前只验收本任务退出标准并保存证据；如未通过，下一次工作从具体失败项继续，不跳阶段，不把未测设备项写成 PASS。

#### 调研如何落到本项目

- Game Developer 将 Boss 视为检验已学技巧的里程碑，并指出战前积累张力、战后释放张力。因此把 5 小关组织为有前置教学的递进弧、胜利后给清楚的结算喘息。此来源支持结构原则，不决定关卡数值或时长。[Boss Battle Design and Structure](https://www.gamedeveloper.com/design/boss-battle-design-and-structure)
- Unity 对 *Evil Wizard* Boss 的开发复盘描述了行为/阶段设计、原型、测试、平衡、视听整合的迭代。因此先在 World 1 做可玩实测，再扩展调数值，避免 12 个世界批量固化未经检验的数值。[How Rubber Duck Games developed a boss fight](https://unity.com/blog/games/how-rubber-duck-games-developed-evil-wizard-boss-fight)
- Microsoft XAG 108 指出难度取决于玩家能力与障碍的组合，建议能保存进度并允许较低强度路径；因此保留 Normal 节点 checkpoint、Hardcore 世界回退及 Zen 练习语义，并以真实玩家结果而非 VM 模拟决定强度。[XAG 108: Game difficulty options](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/108)
- Microsoft XAG 103 的原则是关键信号提供额外通道；结合 XAG 102 的对比度检查，Boss 方向、预警、伤害和可击败状态应结合形状/位置/文案或播报，并验证高对比模式。不能只用粉色变化表达危险。[Xbox Accessibility Guidelines](https://learn.microsoft.com/en-us/xbox/accessibility/guidelines) · [XAG 102: Contrast](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/102)
- 以上是设计研究启发，不是本游戏实测，也不证明 15/20/25 秒任一候选优胜；数值选择只接受 T2 的可复查试玩记录。

### 风险及验证门

- **长局与疲劳：**20 秒 × 60 = 20 分钟小关，不含 Boss。用三种时长原型、分段 checkpoint 和实际玩家反馈确定是否合适，不能因为数学总时长就假称“最佳”。
- **旧时钟旁路：**编写迁移前完整枚举 `t`、`bc`、`wv` 读点与产生全局副作用的地方；Campaign 和旧模式的 Director 只能有一个持有调度权。
- **奖励重复/丢档：**存档和金币、任务、成就、Boss/节点清关同一 v2 快照写；固定事件 id 与模拟崩溃/双击/刷新断言提交前或提交后的唯一结果。现有最高分等独立键不声称与主键原子写入。
- **旧 `.cl` 混义：**v2 的 Campaign 完成独立记录；旧历史关卡记录仍可查看，不作为新 Boss 解锁或奖励依据。
- **Boss 卡点：**先一世界竖切；boss pattern 必须对应玩家在五小关练过的动作；无强制升级门槛；Boss 预警时间和首阶段安全程度由实玩观察。
- **容易刷币/回退：**奖励在节点暂存，只有成功完成对应节点才结算；已领取过的奖励身份不可重复；Hardcore 世界内成果在 Boss clear 前不落账。
- **难度失控：**不要继续依赖整个战役累计 `t`；各节点的速度、间隔、墙缝、追踪物和 Boss 强度都来自显式数据。Boss 以世界等级/节点参数定强度，不以重试次数或重复加载叠强。
- **信息可读性：**Boss 预警、攻势、受伤、可击败和已结算分别使用图形/形状、文字播报和可选音效；高对比、Reduced Motion 都需覆盖。
- **证据边界：**Node 测试证明逻辑边界不证明视觉可见、移动操作、战役时长感、Boss 公平或经济可玩；每个阶段依赖设备和人类验收时，分别写明结果。
